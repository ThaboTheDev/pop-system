# Course Payment and Proof of Payment Management System

A participant payment and proof of payment administration platform for the
MSR Learning Institute, built for 20 000 participants and tens of thousands of
payment records.

**Start with [HANDOVER.md](HANDOVER.md).** Phase 2 replaces participant-backed
registration and custom OTP sessions with applications, Supabase email-link
sign-in and runner capture. The authoritative live database must be confirmed
before any production migration or deployment.

Migration and accounting smoke tests run on real embedded PostgreSQL; strict
TypeScript and the Next.js production build are checked locally. Live Supabase
Auth/Storage and provider delivery must still be exercised against your staging
project before launch. Historical large-seed measurements are in `OPERATIONS.md`.

---

## 1. The stack, and why

| Layer | Choice | Reason |
| --- | --- | --- |
| Frontend and backend | Next.js 15, App Router, React 19, TypeScript | Server Components keep 20 000-row tables on the server. One deployable unit instead of a separate API. Matches the stack already running for the AHV portal. |
| Database | PostgreSQL via Supabase | Relational integrity, real indexes, row level security enforced in the database rather than in the application. |
| Authentication | Supabase Auth | Password hashing, session rotation and reset flows are handled by an audited implementation rather than a hand-rolled one. |
| File storage | Supabase Storage, private bucket | S3-compatible, with signed URLs. No public path to any document. |
| Hosting | Vercel | Same target as your existing projects. |

The one deliberate departure from the brief's suggested stack: there is no
separate Node API service. A separate service would add a network hop, a second
deployment and a second copy of the authorisation rules with nothing gained,
because the security boundary that matters here lives in the database.

## 2. Where the rules live

The most important design decision is that **the database is the enforcement
point, not the application**.

- `amount_paid` is recalculated by a trigger and counts verified payments plus approved signed adjustments.
  A pending or rejected proof can never inflate income, whatever the UI does.
- A rejection without a reason is rejected by `decide_payment()`, not by a form
  validator.
- The audit log is append-only at trigger level. An `UPDATE` or `DELETE` raises
  an exception even for the service role, so a leaked server key cannot rewrite
  history.
- Row level security decides which administrator may read which participant. A
  course admin scoped to one programme cannot read another's rows even through a
  crafted request.

A second front end, a script, or a future mobile app inherits all of this
without reimplementing anything.

## 3. Database schema

```
programmes ──┬── cohorts
             │
             └── participants ──── payments ──┬── pops
                                              ├── payment_verifications
                                              └── notifications
app_users ───── audit_logs
```

| Table | Holds | Notes |
| --- | --- | --- |
| `app_users` | Staff and runners | `id` mirrors `auth.users.id`. Role, active flag, programme scope. |
| `programmes` | Programme and fee | `amount_due` is the single fee, or the original monthly price when `pricing_model` is `dual`. `once_off_amount` is the discounted full payment. |
| `cohorts` | Intakes per programme | Unique on `(programme_id, code)`. |
| `applications` | Applicants awaiting or receiving a staff decision | Consent/version, captured runner, review, agreed fee and optional approved participant link. No participant ID at submission. |
| `participants` | One row per enrolled participant | `participant_ref` (MSRI-001284) is generated by sequence. `full_name`, `outstanding` and `search_vector` are generated columns. `amount_paid`, `pop_count`, `payment_status` are trigger-maintained rollups. |
| `payments` | One row per declared payment | `payment_ref` (PAY-0001234) generated. Carries status, duplicate flag, verification fields. |
| `pops` | Document metadata | Bytes live in Storage. `file_hash` is the sha256, used for duplicate detection. |
| `payment_verifications` | Every status transition | Append-only history, separate from the audit log. |
| `audit_logs` | Every significant action | Append-only, enforced by trigger. |
| `notifications` | Email outbox | Guarded worker claims and delivery outcomes. |
| `account_adjustments`, `payment_plans` | Account operations | Approved adjustments affect rollups; plans track instalments. |
| `bank_statement_lines` | Reconciliation | Batches with matched, unmatched and ignored states. |
| `resubmit_tokens` | Server-only clarification links | Hashed random tokens, expiry and single-use state. Portal authentication uses Supabase Auth, not this table. |

Participant information is stored once. Payments reference participants by
foreign key; no name or email is copied across tables.

### Key functions

| Function | Purpose |
| --- | --- |
| `submit_application(...)` | Records versioned consent and an application; no participant/ID/fees yet. |
| `approve_application(...)`, `decline_application(...)` | Staff-only transactional decision, participant creation on approval, audit and outbox. |
| `claim_participant_account()` | Links a verified non-staff Auth identity by email; RLS then permits only its own record. |
| `capture_runner_payment(...)` | Records money taken in person as pending; never verifies. |
| `submit_payment(...)` | Creates the payment, attaches the PoP, runs duplicate detection, queues the notification and writes the audit line, in one transaction. |
| `decide_payment(...)` | Applies a verification decision with its history entry, audit line and notification. Refuses a rejection with no reason. |
| `recalculate_participant(id)` | Rebuilds a participant's rollups from `payments`. Locks the row, so concurrent verifications serialise. |
| `detect_duplicate_payment(id)` | Flags on same participant/amount/date, reused reference, or identical document hash. Never deletes. |
| `dashboard_stats(programme?)` | Every dashboard figure in one round trip. |
| `global_search(query, limit)` | Searches participant ref, name, email, mobile, payment ref and bank reference. |
| `programme_report`, `monthly_payment_report`, `daily_payment_report` | Report aggregates. |

### Verification statuses

`pending_review`, `under_review`, `verified`, `rejected`, `duplicate`,
`requires_clarification`.

Duplicate detection sets a `duplicate_flag` and leaves the payment in the queue,
rather than moving it straight to `duplicate`. The flag is a prompt to an
administrator; the status is the administrator's conclusion.

## 5. Setup

```bash
git clone <your-repo> && cd pop-system
npm ci
# Create .env.local from the template in ENVIRONMENT.md and fill in your
# Supabase project values.
```

Apply the schema, in order:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -1 -f supabase/migrations/0001_schema.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -1 -f supabase/migrations/0002_functions.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -1 -f supabase/migrations/0003_security.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -1 -f supabase/migrations/0004_operations.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -1 -f supabase/migrations/0005_email_only.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -1 -f supabase/migrations/0006_registration.sql
# Separate transactions: 0007 must commit before 0008 uses the enum values.
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -1 -f supabase/migrations/0007_runner_role.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -1 -f supabase/migrations/0008_registration_portal.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -1 -f supabase/migrations/0009_programme_pricing.sql
```

Seed. The file defaults to 20 000 participants; change `v_participants` near the
top to 120 for a light demo database.

```bash
psql "$DATABASE_URL" -f supabase/seed/seed.sql
```

Create the first administrator, then sign in at `/login`:

```bash
node --env-file=.env.local scripts/create-admin.mjs \
  "finance@msri.online" "a-long-passphrase" "Tshidiso Gama" super_admin
npm run dev
```

The participant form is at `/submit`; self-service is at `/portal`; new applicants register at `/register`. The portal sign-in entry is `/portal/login`. Configure Supabase Auth SMTP/callback URLs for sign-in links and Resend separately for outbox mail.

### Environment variables

| Variable | Used by | Notes |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | browser and server | Project URL. |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | browser and server | Safe to expose; RLS governs it. (Previously misnamed `…_PUBLISHABLE_KEY` in an older template.) |
| `SUPABASE_SERVICE_ROLE_KEY` | server only | Bypasses RLS. Never expose, never commit. |
| `DATABASE_URL` | migrations and seeding only | Use a direct or session-pooler connection suitable for DDL; the app itself uses Supabase’s API. |
| `POP_BUCKET` | server | Defaults to `proof-of-payment`. |
| `POP_SIGNED_URL_TTL` | server | Minutes a signed link lives. Default 5. |

## 6. The workflow

```
Participant registered, holds MSRI-001284
        ↓
Pays, opens /submit on their phone, attaches the receipt
        ↓
submit_payment() writes the payment, attaches the file,
runs duplicate detection, queues the notification, writes the audit line
        ↓
Status: Pending review. It does NOT count towards income.
        ↓
Finance administrator opens /verification, oldest first
Participant on the left, document on the right, controls below
        ↓
Verify · Reject · Mark duplicate · Request clarification · Add note
        ↓
decide_payment() records the decision, the history entry,
the audit line and the participant notification
        ↓
If verified: the trigger recalculates amount_paid, outstanding
and payment status
        ↓
Dashboard, reports and exports reflect it immediately
```

## 7. Registration and access control

### Administrator sign-in: work email and password, no second factor

Sign-in is work email and password only. The previous in-app TOTP step was
removed deliberately — the TOTP challenge is gone from the sign-in form, and
the `aal2` requirement is gone from `currentUser()`. The two had to move
together: removing only the form would have locked every administrator out of
the admin area while the screen looked like it wanted a password alone, and
the enrolment component was deleted rather than left in place to challenge
nothing.

The honest trade-off, recorded here rather than in a commit message:

- **What was given up.** A guessed or phished password is now sufficient on
  its own. Supabase Auth still owns password hashing, session rotation and
  the reset flow, but nothing beyond the password stands between an attacker
  and a session.
- **What stands in its place (the compensating controls).** Row level
  security on every table with a default-deny posture; role checks inside the
  SQL functions themselves (`decide_payment`, `approve_application`, …), so
  a crafted request fails in the database regardless of what the application
  let through; the append-only audit log, which even the service role cannot
  rewrite; and server-only secrets — the service-role key never leaves the
  server, and the public write paths (`/submit`, `/register`) go through
  checked, rate-limited server actions.
- **Restoring the factor is a small revert.** Put the challenge field back in
  `LoginForm.tsx`, the `aal2` check back in `currentUser()` and the enrolment
  card back on Settings. Until then: long passphrases, prompt suspension of
  leavers, and an eye on the audit log.

### How participants join the register

- **Staff capture or bulk import** remains a trusted registry workflow for
  already-enrolled people.
- **Public `/register` and runner `/runner/register`** write `applications`, not
  `participants`. Consent, timestamp, notice version and collection method are
  stored on that application. Dual-price programmes also record whether the
  applicant chose the discounted once-off amount or the original monthly price.
  Duplicate submissions do not create a second row.
- Staff review at `/applications`, oldest first. Finance/super administrators
  approve with the current programme fee or a bursary override; only then does
  `approve_application()` create the participant and ID. Declining requires a
  reason. Both decisions commit with their audit entry and outbox notification.
- Unapproved applications cannot inflate participant counts/outstanding totals
  or accept payments: no participant record or payment reference exists for them.

### Participant portal and runners

`/portal/login` sends a Supabase email link to the institute-held email, with no
password or Participant ID. `/auth/callback` exchanges the PKCE code and `/portal`
calls `claim_participant_account()`. The database matches a verified Auth email,
refuses staff accounts and ambiguous addresses, and grants own-record access via
`participants_self_read`, `payments_self_read` and `pops_self_read`. All portal
queries carry the participant JWT; there is no service-role data-read bypass.
Unknown addresses get a polite dead end. Details are read-only; history is paginated.

The `runner` role has a phone-friendly workspace at `/runner`. It captures only
its own applications and records in-person money at `/runner/capture`. Payments
are pending until independently verified by finance. Runners cannot approve
applications, verify/update payments, export the register or read the audit log.
These restrictions are enforced in SQL/RLS, not just navigation.

See `HANDOVER.md` for the data-preserving upgrade, role tests, restrictive Auth
signup support and required SMTP/redirect configuration. The old `/registrations`
and OTP portal URLs are redirects only; their actions, cookies, functions and
OTP table are retired by migration 0008.

## 8. Operations layer and remaining scope

### Included

- Streaming queue badges, navigation progress, CSS content skeleton and short tab cache.
- Separate applications, approval-time participant IDs and bursary fees; versioned
  POPIA consent and runner declarations, with transactional audit/outbox records.
- Password-only administrator sign-in; password reset via PKCE or fragment
  session (§7 records the trade-off).
- Resend email outbox, post-response delivery, daily queued-mail sweep and operator retry.
- Supabase email-link participant portal with own-row RLS, phone-friendly runner
  capture, single-use clarification links and up to three submission documents.
- Signed adjustments, monthly payment plans and reminders, bank CSV reconciliation,
  verified receipts and account statement PDFs (latest 40 payments).
- Atomic verification claims, bulk decisions, all-document links, resubmit-link delivery.
- Administrator invitations, role/scope management, reset emails; programme/cohort CRUD;
  participant editing, staff capture, merge and anonymization.
- New-participant import, update-existing import and payment batches; arrears,
  throughput and duplicate reports with CSV exports.

### Not included / deployment caveats

- **No SMS, accounting-system integration, or background exports.** CSV exports run
  in the request. Bank reconciliation does not automatically verify income.
- Provider acceptance is not proof of final delivery. There are no delivery webhook
  receipts or automatic retry/backoff; investigate failed/skipped/processing rows.
- Payment submission and decision emails are queued transactionally in Postgres.
  Legacy non-email records are retained for history but cannot be requeued.
- Imports commit row-by-row and report partial progress; payment batches must not be
  blindly retried. Duplicate detection flags repeated submissions for review.
- Public IP rate limiting is per process; use a shared edge/Redis limiter for production.
- The 32 MB Server Action limit does not override your host's smaller request limit.
  Use a host accepting that payload size or add a signed direct-upload flow before
  promising 10 MB files on a platform with a smaller cap.
- No live provider or browser end-to-end testing is implied by a clean build. Follow
  the go-live checklist in `OPERATIONS.md`.

### Verification

```bash
npm ci
npm run typecheck
npm run build
npm test
```

`npm test` runs the existing operations suite against all nine migrations and a
separate Phase 2 suite on temporary real PostgreSQL. The latter checks the legacy
upgrade, consent, duplicate/concurrent applications, approval-time IDs, bursaries,
runner restrictions, and participant isolation against 20,001 rows. Auth/storage
schemas are stubbed. A third suite executes portal, callback, registration and
role helpers with mocked dependencies. No live data or email provider is touched.

See `ENVIRONMENT.md` for APP_URL, Supabase Auth SMTP, ORG_NAME, RESEND_* and
CRON_SECRET configuration. Configure secrets in your host, never in Git.

## 9. Design

The interface follows the institute's own visual language rather than a generic
admin theme, so an administrator moving between the MSRI website and this system
sees one institution. The palette, type stack and component treatments are taken
from the website's own stylesheet (`msri-website: assets/css/global.css` and
`components.css`).

| Token | Value | Carries |
| --- | --- | --- |
| `--navy` | `#0b113b` | Structure: sidebar, page band, headings, primary buttons |
| `--navy-light` | `#151e54` | The second stop of the band gradient, stat card top rules |
| `--gold-solid` | `#cba65e` | The accent: gold rules, the main action on a screen, active tab |
| `--gold` | `#e9c176` | Gold that sits on navy — band headings and figures |
| `--gold-ink` | `#85651b` | Gold text on white, darkened to pass contrast |
| `--indigo` | `#4a54c1` | Under review, matching the website's accreditation badge |
| `--surface` | `#f8fafc` | Page ground (`--bg-light` on the website) |

Rules the CSS follows:

- **Navy is structure, gold is the one accent.** Gold marks a section title
  (the rule under an `h2`), the screen's single most important action
  (`btn-gold`), and the active navigation tab. Nothing else uses it, so it keeps
  meaning something.
- **State owns the rest of the colour.** Green, amber, red and indigo are
  reserved for payment state and notices; they are never decorative.
- **The catalogue label.** `PageHead` renders the website's label row — a 60 px
  gold rule, then small uppercase wide-tracked text — above every page title, and
  `.card-flush` carries the 4 px gold top border used on the website's cards.
- **Type is the institute's stack** (Candara, Calibri, Segoe UI, Optima). It is
  a local font stack, so no webfont is downloaded and the CSP is unchanged.
- **The crest** is `public/branding/msri-logo.png`. It is navy on white, so it
  sits on a white plate in the sidebar, the sign-in panel and the participant
  portal rather than directly on the navy.
- Accessibility is unchanged in kind: focus rings are still drawn (in gold),
  figures keep tabular numerals, and gold used as text is darkened until it
  passes contrast on white.

Where it lives:

| File | Holds |
| --- | --- |
| `src/app/globals.css` | Every token and component rule. Class names are unchanged, so the whole system restyled from one file — including the pages added by the operations layer. |
| `src/components/PageHead.tsx` | Page heading: gold label, navy title, supporting line, actions. |
| `src/components/Brand.tsx` | The crest and the sidebar lockup. |
| `public/branding/msri-logo.png` | The institute's crest, as used on the website. |
| `design/preview.html` | A static reference of every screen and control, for review without a database. Self-contained: `npm run preview:css` inlines the real stylesheet and the crest into it, so it opens from disk with zero external requests. It is not part of the build and is not shipped. |

One configuration note: production still refuses to be framed
(`X-Frame-Options: DENY`, `frame-ancestors 'none'`). `next.config.ts` relaxes
those two headers in development only, so the app can be shown inside a local
preview pane. The deployed headers are unchanged.
